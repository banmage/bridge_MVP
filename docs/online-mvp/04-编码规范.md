# 04 编码规范（联网 MVP）

**版本**: v1.0  
**状态**: 评审通过（2026-11-01）  
**适用范围**: `src/`、`server/`、`shared/`、测试与文档

## 1. 基本原则

1. **权威单一**：对局状态只存在于服务端；客户端不推导权威状态。
2. **单点复用**：法律、规则解析、AI、计分不得在前后端复制。
3. **先校验后变更**：任何动作先完成全部校验，再修改状态；错误路径不产生副作用。
4. **显式优于隐式**：类型、错误码、协议字段必须显式；不依赖隐式 `any`。
5. **小步可回滚**：每个提交可独立构建、测试、回滚。

## 2. 目录与分层

```text
shared/       前后端共享的类型与纯函数（无 DOM、无 Node API）
src/core/     桥牌法律与计分（纯函数、无 UI/网络）
src/engine/   规则解析、匹配、裁决（纯函数优先）
src/ai/       机器人策略（输入状态，输出动作）
src/models/   领域模型与类型
src/net/      浏览器网络层（WebSocket / HTTP）
src/store/    Pinia 状态与动作
src/components/ 展示组件
src/views/    路由页面
server/       Node 服务端（可 import src/core|engine|ai|models、shared）
```

**依赖方向**：`server → shared/src core`；`src → shared`；禁止 `src` 反向依赖 `server`。

## 3. TypeScript 规范

- 开启 `strict`；不使用 `any`，确需逃逸时用 `unknown` + 类型收窄，并写明原因。
- 类型导入使用 `import type`；仅类型依赖不得产生运行时 import。
- 联合类型优先于布尔标志；错误用 `Error` 子类（如 `MatchError`）携带错误码。
- 公共函数写返回类型；内部短函数可推断。
- 命名：
  - 类型/接口/枚举：`PascalCase`；
  - 变量/函数/方法：`camelCase`；
  - 常量：`UPPER_SNAKE_CASE`；
  - 文件：`camelCase.ts`，Vue 组件 `PascalCase.vue`。
- 空值：优先 `null` 表示“无”，避免同时混用 `undefined` 与 `null`；可选字段用 `?`。
- 纯函数不修改入参；需要复制时显式展开/深拷贝，避免共享引用泄漏。
- 时间与随机：通过注入 `now` / `rng` 保证可测试、可复现。

## 4. Vue 3 规范

- 统一 `<script setup lang="ts">`；组件名文件 `PascalCase.vue`。
- Props/Emits 显式类型；禁止直接修改 props。
- 全局状态只通过 Pinia store；组件不直接发 WebSocket。
- 服务端快照是只读的：组件不得就地修改 `room/board` 对象。
- 交互禁用条件由 `canAct` 等服务端字段驱动，不自行猜测轮次。
- 列表渲染必须提供稳定 `key`；避免用索引作为可变列表 key。
- 样式使用 `<style scoped>`；跨组件主题变量放在 `src/style.css`。
- 文案使用中文，保持一致术语：叫牌、出牌、明手、定约、贴点制、双人赛。

## 5. Node/服务端规范

- 服务端模块不得依赖 DOM；只使用 Node API 与共享纯函数。
- 所有客户端输入视为不可信：校验类型、范围、身份、轮次、法律。
- 动作处理顺序固定：**身份 → 房间 → 阶段 → 轮次/控制权 → 法律 → 提交 → 广播**。
- 抛错使用 `MatchError(code, message)`；`GameHub` 统一转 `error` 报文。
- 错误信息面向玩家、可读；不泄露内部堆栈/路径。
- 定时器必须 `unref()`（生产）并支持注入（测试）；每个房间最多一个 AI 定时器。
- 广播只通过 `projectRoomView`；禁止把内部 `Room/MatchEngine` 直接序列化。
- 落盘使用“临时文件 + rename”；失败不阻断对局。
- 新增环境变量必须：有默认值、写入 README/运行手册、在 `server/index.ts` 集中读取。

## 6. 协议规范

- `shared/protocol.ts` 是报文与视图的单一事实来源。
- 新增字段优先可选，保持向后兼容；不兼容变更递增 `PROTOCOL_VERSION`。
- 错误码只增不改语义；新增码同步协议契约与测试。
- 客户端/服务端都不得发送未在协议中声明的字段。
- 未知报文类型忽略（前向兼容）；非法 JSON 返回 `BAD_REQUEST`。

## 7. 安全规范

- 严禁把 `token`、`seed`、他人手牌、内部状态写入任何出站报文。
- 视角裁剪只在 `server/view.ts` 实现；其他模块不得自行拼装 `RoomView`。
- 不信任客户端提交的 `playerId/seat/persona`：服务端必须重新校验/清洗。
- 聊天、昵称、人格字段必须截断/白名单。
- WebSocket 设置 `maxPayload`；生产环境强制 TLS。
- 日志不得打印 token 或完整手牌。

## 8. 测试规范

- 框架：Vitest；前端默认 happy-dom，服务端引擎/协议测试使用 `// @vitest-environment node`。
- 命名：`describe('能力')` + `it('行为与预期')`，中文可读。
- 每个缺陷修复必须附回归测试；每个 FR 至少有一个自动化断言或手工验收记录。
- 测试必须确定性：注入 `now`/`rng`/定时器；禁止真实等待与网络。
- 断言优先行为而非实现细节；视角/安全类测试必须断言“不存在”而非仅“存在”。
- 测试数据构造使用工厂函数，避免复制大段 fixture。
- 不提交 `.only`、跳过测试或空断言。

## 9. 错误与日志

- 用户可见错误：中文、可操作；例如“必须跟出领出花色”。
- 内部错误：`console.error` 仅用于不可恢复异常；正常业务错误不打日志。
- 生产建议接入结构化日志：`level/time/roomCode/playerId/event/code`，不记录敏感数据。
- 禁止吞掉异常后继续修改状态；要么回滚，要么不修改。

## 10. Git 与提交规范

- 分支：`main` 为可发布分支；特性/修复用短分支。
- 提交信息：`<type>: <中文摘要>`，type 取 `feat/fix/refactor/test/docs/chore`。
- 一个提交只做一件事；格式化/重命名不与逻辑修改混合。
- 提交前必须通过：`npm test`、`npm run typecheck`、`npm run typecheck:server`。
- 不提交 `node_modules/`、`dist/`、`server/data/`、日志与本地密钥。

## 11. 代码评审清单

### 正确性

- [ ] 服务端是否重新校验了身份/房间/阶段/轮次/法律？
- [ ] 错误路径是否保证状态不变？
- [ ] 明手/庄家控制权是否正确？
- [ ] 结算与计分是否与 `core` 一致？

### 安全

- [ ] 出站报文是否只经过 `projectRoomView`？
- [ ] 是否泄漏 token/seed/他人手牌？
- [ ] 输入是否截断/白名单/类型校验？

### 并发与生命周期

- [ ] 定时器是否可取消、是否 `unref`？
- [ ] 断线/重连/接管/离开是否清理状态？
- [ ] 房间结束时是否停止 AI 调度？

### 测试与文档

- [ ] 新增/修改行为是否有测试？
- [ ] 是否覆盖失败路径与边界？
- [ ] 协议/环境变量/文档是否同步？
- [ ] 是否通过全量类型检查与构建？

## 12. 完成定义（DoD）

一个任务只有同时满足以下条件才算完成：

1. 代码实现并通过 `typecheck` / `typecheck:server`；
2. 关键路径有自动化测试，全量测试通过；
3. 无新增 TODO/FIXME，无调试输出；
4. 协议/配置/文档同步更新；
5. 通过代码评审清单；
6. 可构建、可部署、可回滚。
