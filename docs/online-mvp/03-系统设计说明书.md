# 03 系统设计说明书（联网 MVP 一期）

**版本**: v1.1  
**状态**: 设计评审通过（2026-11-01，CR-006 补充于 2026-11-02）  
**关联**: [`plan.md`](../../specs/001-online-pair-game/plan.md)、[`data-model.md`](../../specs/001-online-pair-game/data-model.md)

## 1. 设计目标

1. **服务端权威**：所有对局动作在服务端校验，客户端只能提交意图。
2. **视角隔离**：每个连接只收到按 `playerId` 裁剪的快照，从根上防止作弊。
3. **单点复用**：法律、规则解析、AI、计分在前后端共用，不复制实现。
4. **可复盘**：每副保留 seed、四手牌、叫牌、出牌与计分依据。
5. **可重连**：断线保留座位；超时托管保证比赛可完成。

## 2. 总体架构

```text
┌──────────────────────────── 浏览器 ────────────────────────────┐
│ Vue 3 SPA                                                      │
│  LobbyView ─ RoomView ─ OnlineTable / SouthPlayed / ScoreTable │
│        │           │                                           │
│        └── Pinia online store ── OnlineSocket（自动重连/心跳）  │
└───────────────────────────────┬────────────────────────────────┘
                                │ /ws（JSON 报文） + /api（HTTP）
┌───────────────────────────────▼────────────────────────────────┐
│ Node + ws 单进程                                                │
│  index.ts：HTTP/静态托管/健康检查/心跳/ticker                   │
│  GameHub：身份、会话、分发、广播、AI 调度、落盘触发             │
│   ├─ RoomManager：房间/座位/配置/开赛/离开/超时托管            │
│   ├─ MatchEngine：发牌/叫牌/出牌/结算/记录（唯一权威）          │
│   ├─ roomSnapshot：进行中房间原子写 / 启动恢复 / 结束清理       │
│   ├─ view.ts：projectRoomView（唯一出口）                       │
│   ├─ reference.ts：MP 7 桌对照场                                │
│   ├─ personas.ts：人格 → 风格/规则/提醒                         │
│   ├─ rules.ts：YAML 读取缓存                                    │
│   └─ persistence.ts：JSON 原子写 + 查询                         │
│  共享：src/core（法律）、src/engine/parse（YAML）、src/ai       │
└─────────────────────────────────────────────────────────────────┘
```

**关键决策**：单进程 Node + `ws`；全量快照 + 意图；服务端投影；文件系统 JSON 持久化。
详细取舍见 [`research.md`](../../specs/001-online-pair-game/research.md)。

## 4. 关键流程

### 4.1 建房与加入

1. 客户端发送 `createRoom {config, seat}`；
2. `RoomManager.createRoom` 校验配置、生成房间码与 `matchId/seedBase`；
3. `GameHub` 广播 `RoomView` 给房内连接；
4. 其他玩家 `joinRoom {code, seat}`；服务端校验座位并同步。

### 4.2 身份与重连

1. 客户端首次生成 `playerId + token` 存 `localStorage`；
2. 连接后首条必须是 `hello`；token 不匹配则 `AUTH_FAILED` 并关闭；
3. 同一身份新连接生效，旧连接收到 `DUPLICATE_SESSION` 并关闭；
4. 断线只标记 `connected=false` 并保留座位/手牌；
5. 重连时 `markConnected` 恢复在线，广播快照；客户端收到 `hello` 后主动 `joinRoom` 兜底；
6. 开赛后断线超过 `BOT_TAKEOVER_MS`（默认 60s）由机器人接管。

### 4.3 开赛

1. 房主 `startMatch`；校验房主、`lobby`、四座已满；
2. 构造 `EngineSeat`（真人带 `playerId`，机器人带人格）；
3. `MatchEngine.start()` 发第 1 副；`Room.status='playing'`；
4. `afterAction` 广播并调度 AI。

### 4.4 叫牌/出牌

```text
客户端 bid/play
  → GameHub.dispatch
  → RoomManager.requirePlayingRoom
  → MatchEngine.submitBid/submitPlay
      → 校验阶段/轮次/控制权/法律
      → 修改状态 / 结算
  → afterAction: noteSettlement → persist? → broadcast → scheduleAi
```

- 人类控制：`controllerOf(seat)`；明手由庄家代打。
- 非法动作抛 `MatchError`，由 `GameHub` 转成 `error` 报文；**状态不变**。
- 机器人走同一 `applyBid/applyPlay`，只是由服务端定时器触发。

### 4.5 结算与下一副

1. 第 13 墩或四家 Pass → `phase='scored'`；
2. `finalizeBoard` 计算得分/IMP/点数/MP；
3. `noteSettlement` 设置自动开副时间或标记比赛结束；
4. `broadcast` 下发结算视图；`ticker` 到点自动 `nextBoard`；
5. 最后一场结束：`room.status='finished'`，落盘一次。

### 4.6 断线托管

- `markDisconnected` 记录 `awaySince`；
- `ticker` 每秒调用 `takeoverExpired(room, BOT_TAKEOVER_MS)`；
- 超时后座位转机器人、`match.takeoverSeat`、从 `joinOrder` 移除；
- 若被接管者是房主，转给仍在座真人；无真人则房主置空，避免“幽灵房主”。

### 4.7 重启恢复

- 开赛后每次状态变更（叫牌/出牌/结算/聊天/入座/断线）都会把房间写入
  `server/data/rooms/<code>.json`（`ROOM_DATA_DIR` 可覆盖，临时文件 + rename 原子写）；
- 快照包含房间配置、座位、聊天、当前副的完整 `BoardState`、已完成副与 AI 随机源状态，
  不含 token，也不会下发给客户端；
- 进程启动时 `RoomManager.restoreRooms` 读回快照，所有真人座位先标记离线并重新开始
  `BOT_TAKEOVER_MS` 倒计时；`GameHub.resume` 续跑机器人、自动开下一副；
- 客户端用原 `playerId + token` 重连即回到原座位与当前副；无人重连的座位超时后由机器人接管；
- 比赛结束时先写正式记录，成功后删除房间快照，避免重启后重复恢复；
- 损坏或版本不匹配的单条快照会被跳过，不影响其他房间。

## 5. 数据模型

以 [`data-model.md`](../../specs/001-online-pair-game/data-model.md) 与
[`shared/protocol.ts`](../../shared/protocol.ts) 为准。核心实体：

- `Player`：设备身份；
- `Room`：code/hostId/status/config/seats/match/chat；
- `Seat`：open / human / bot；
- `MatchConfig`：boards、scoring、seedBase、matchId；
- `BoardState/BoardRecord`：seed、dealer、vulnerability、hands、bidding、tricks、contract、score、scoring；
- `RoomView/BoardView`：按玩家裁剪的只读投影。

**服务端内部字段**（`seed`、`allHands`、`awaySince`）不进入投影。

## 6. 协议设计

完整定义见 [`contracts/protocol.md`](../../specs/001-online-pair-game/contracts/protocol.md)。

### 6.1 客户端 → 服务端

`hello`、`setName`、`createRoom`、`joinRoom`、`leaveRoom`、`setSeat`、`updateBot`、
`setConfig`、`startMatch`、`bid`、`play`、`nextBoard`、`chat`、`requestState`、`ping`。

### 6.2 服务端 → 客户端

`hello`、`room`、`error`、`toast`、`pong`。

### 6.3 错误码

`AUTH_FAILED`、`DUPLICATE_SESSION`、`NOT_IN_ROOM`、`NOT_HOST`、`ROOM_NOT_FOUND`、
`ROOM_FULL`、`SEAT_TAKEN`、`WRONG_PHASE`、`NOT_YOUR_TURN`、`ILLEGAL_BID`、
`ILLEGAL_PLAY`、`SEATS_NOT_FULL`、`INVALID_CONFIG`、`BAD_REQUEST`。

### 6.4 版本策略

- `PROTOCOL_VERSION` 不兼容变更时递增；
- 未知报文类型前向兼容（忽略）；
- 非法 JSON/版本不匹配返回 `BAD_REQUEST`。

## 7. 视角隔离设计

`projectRoomView` 是唯一出站状态构造器，不变量：

1. `yourHand` 只含 `yourSeat` 的手牌；结算后为 `null`（改用 `revealedHands`）；
2. `dummyHand` 仅在 `dummyOpen && !scored` 时存在；
3. `revealedHands` 仅在 `phase==='scored'` 时存在，四手各 13 张；
4. `BoardView` 不含 `seed`；`RoomView` 不含 token；
5. 真人座位只暴露 `playerId/name/connected`，机器人只暴露人格。

自动化断言见 `server/__tests__/view.test.ts`。

## 8. 计分设计

### 8.1 标准复式

每副用 `computeScore` 计算 NS/EW 得分；流局双方 0。

### 8.2 贴点制

复用 `hcpAdjustedPoints`：`IMP − (胜方联手大牌点 − 20)`；流局按大牌点方向贴点。
逐副累计为 `NS/EW` 点数与胜负。

### 8.3 MP 对照场

- 同一副牌、同 seed，模拟 7 桌“正常/精确/随机度 0”机器人；
- 本桌 NS 得分与 7 桌结果比较，得到 `0..100` 百分比；
- 对照场结果存入 `BoardScoring.referenceResults`，可复算；
- 由 `RoomManager` 注入 `simulateReferenceScores`，测试可替换。

## 9. 并发与状态机

### 9.1 房间

```text
lobby ──startMatch──▶ playing ──last board──▶ finished
```

### 9.2 单副

```text
bidding ──3 passes after bid──▶ play_waiting_lead ──lead──▶ play
bidding ──4 passes────────────▶ scored
play ──13th trick─────────────▶ scored
scored ──nextBoard────────────▶ (next bidding | finished)
```

### 9.3 串行化

- Node 单线程事件循环；每个报文处理是同步的，天然串行；
- 两个客户端同时提交：先到者推进轮次，后到者因轮次不符被拒绝；
- AI 定时器每个房间最多一个，执行后重新调度。

## 10. 失败处理

| 场景 | 处理 |
|------|------|
| 非法 JSON / 版本不匹配 | `BAD_REQUEST`；版本不匹配关闭连接 |
| 未认证 | 首条非 hello → `AUTH_FAILED` 并关闭 |
| 重复连接 | 新连接生效，旧连接 `DUPLICATE_SESSION` 并关闭 |
| 非法动作 | `MatchError` → `error`；状态不变 |
| 机器人异常 | 捕获并广播当前状态，避免死循环 |
| 落盘失败 | 不阻断对局；下次结算/查询可重试 |
| 房间快照失败 | 不阻断对局；下一次动作重试；正式记录成功后删除快照 |
| 进程重启 | 从快照恢复进行中房间；真人重新开始托管倒计时 |
| 断线 | 保留座位；超时托管 |
| 房间解散 | 客户端收到 `ROOM_NOT_FOUND` 后清空本地状态 |

## 11. 安全设计

- 服务端权威，客户端无写状态能力；
- 视角投影唯一出口，测试断言无泄漏；
- token 只用于 hello 校验，不下发；
- seed 不进入客户端视图；
- WebSocket `maxPayload=64KB`，聊天 200 字，昵称 20 字；
- 房间码 6 位 `[A-Z0-9]`，碰撞重试；
- 生产部署建议 TLS（`wss://`）与反向代理限流。

## 14. 设计决策记录（ADR）

| ADR | 决策 | 理由 |
|-----|------|------|
| ADR-01 | Node + `ws` 单进程 | 复用 TS 规则/AI，零语言切换；一期规模足够 |
| ADR-02 | 全量快照 + 意图 | 简单、抗丢包、重连容易 |
| ADR-03 | 服务端投影 | 从根上防作弊 |
| ADR-04 | 7 桌机器人对照场 | 单桌也能产生 MP 名次，可复现 |
| ADR-05 | 文件系统 JSON | 一期无数据库需求，易部署 |
| ADR-06 | 设备身份 `playerId+token` | 免注册，满足重连 |
| ADR-07 | 断线超时托管 | 保证比赛可完成，避免永久卡局 |
| ADR-08 | 进行中房间写本地快照并启动恢复 | 单实例部署下低成本消除重启丢局；二期多实例再换共享存储 |

## 15. 已知限制

- 进行中房间快照保存在本地文件，仅适用于单实例部署；多实例需共享存储（二期）；
- 快照只保证进程重启恢复，不替代数据库事务；
- 无公开观战/观众席；
- 无比赛时限与超时判负；
- 单进程容量有限，未做水平扩展；
- 日志为 `console`，未接入结构化日志/指标系统。
