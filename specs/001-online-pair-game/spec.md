# Feature Specification: 联网双人赛与贴点制对局（一期）

**Feature Branch**: `001-online-pair-game`

**Created**: 2026-11-01

**Status**: Draft

**Input**: User description: "基于目前的叫牌和打牌的客户端界面，将该项目拓展为一个联网游戏。第一期开发一个我与同伴（同伴可以是真人，也可以选择一个 AI 机器人，由我设置它的名字、风险偏好、叫牌体系、附加约定等）参加双人赛（可以选择 12、18 或 24 副牌）或者贴点制比赛，并记录叫牌打牌过程，最后统计成绩；也可以是我选 AI 机器人与朋友选 AI 对抗。第二期可以开发队式赛或类似联众的全场赛。"

## Clarifications

### Session 2026-11-01

- Q: 一期「双人赛」如何在没有多桌的情况下产生名次？ → A: 每副牌由服务端用同一发牌生成 **7 桌机器人对照场**（可播种），按 MP（比赛分）百分比结算；对照场结果随记录存档，可复算。
- Q: 「贴点制」计分口径？ → A: 沿用现有 `core/imps.ts` 的 `hcpAdjustedPoints`（本副点数 = IMP −（胜方联手大牌点 − 20）），逐副累加。
- Q: 账号体系？ → A: 一期不做密码账号；客户端持久化一个设备级 `playerId + token`，昵称可改，用于重连与身份识别。
- Q: AI 在哪里运行？ → A: 服务端。AI 与真人共用动作入口；机器人不会拿到他人手牌。
- Q: 一期是否要求断线重连？ → A: 要求。断线保留座位与手牌，重连后恢复同一视角快照。
- Q: 是否允许旁观？ → A: 一期只允许本桌 4 名占用者（真人或其机器人）与房主旁观；公开观战列入二期。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 创建房间并开始一场 12/18/24 副的比赛（Priority: P1）

作为玩家，我在大厅创建房间，选择比赛副数（12/18/24）与计分模式（双人赛 MP / 贴点制），
选定自己的座位，把其余座位设置为「邀请真人」或「AI 机器人」，然后开始比赛。

**Why this priority**: 没有房间与开赛就没有联网对局，这是全部功能的地基。

**Independent Test**: 单人即可验证：建房 → 三个座位填机器人 → 开赛 → 连续完成 12 副 → 出成绩页。
全过程无需第二名真人。

**Acceptance Scenarios**:

1. **Given** 玩家在大厅，**When** 创建房间并选择 18 副 / 贴点制，**Then** 获得 6 位房间码，进入房间，房主为自己所在座位。
2. **Given** 房间内 4 个座位均已占用且房主已开赛，**When** 服务端开始第 1 副，**Then** 按标准轮转给出庄家与局况，四位占用者收到各自的视角快照。
3. **Given** 比赛进行到第 12 副结束，**When** 最后一副结算完成，**Then** 比赛状态变为「已结束」，成绩页展示逐副成绩与总计。
4. **Given** 座位未填满，**When** 房主点击开赛，**Then** 服务端拒绝并提示「还有空座位」。

---

### User Story 2 - 配置 AI 同伴/对手（名字、风险偏好、叫牌体系、约定）（Priority: P1）

作为玩家，我可以为任意 AI 座位设置人格：名字、风险偏好（保守/正常/激进）、叫牌体系（精确/自然）、
附加约定（如强无将、负加倍、弱二开叫等开关），并能在房间内看到这些设置。

**Why this priority**: 「同伴可以是 AI 且由我配置」是本次需求的核心差异点。

**Independent Test**: 创建房间 → 把 N 座设为 AI「小满 / 激进 / 自然 / 负加倍」→ 开赛后该座位的叫牌
风格与提醒文本符合配置（叫牌记录中带约定提醒）。

**Acceptance Scenarios**:

1. **Given** 房主在房间内，**When** 为东家添加机器人并设置名字「EastBot」、风险「保守」、体系「精确」，**Then** 座位面板显示该人格，其他玩家同步看到。
2. **Given** 机器人被配置为「自然」体系，**When** 同样牌型轮到它开叫，**Then** 其叫牌序列与「精确」体系不同（可通过记录对比验证）。
3. **Given** 机器人配置了「负加倍」约定，**When** 它使用该约定叫品，**Then** 叫牌记录附带提醒文本，对手可见。
4. **Given** 玩家设置随机度为 0，**When** 用相同发牌种子重放，**Then** 机器人的叫牌与出牌完全一致。

---

### User Story 3 - 两名真人各自带 AI 同伴同桌对抗（Priority: P1）

我（南家）与我的 AI 同伴（北家）对抗朋友（东家）与其 AI 同伴（西家）。

**Why this priority**: 这是需求中明确点名的第二种玩法，验证「多真人 + 多机器人混排」与视角隔离。

**Independent Test**: 两个浏览器会话：A 建房坐南、北家机器人；B 用房间码加入坐东、西家机器人；开赛后
A 只能看到南家与（首攻后的）明手牌，B 只能看到东家与明手牌，双方看到的叫牌/出牌一致。

**Acceptance Scenarios**:

1. **Given** A 已建房且南/北座就绪，**When** B 输入房间码加入并选择东家座位，**Then** 双方座位面板同步更新。
2. **Given** 比赛进行中，**When** A 查看自己的快照，**Then** 其中不含东家、西家的手牌（除非已公开为明手或本副结束）。
3. **Given** B 断线 30 秒后重连，**When** 使用同一设备身份重连，**Then** 回到东家座位且手牌、叫牌、当前轮次不丢失。
4. **Given** 轮到非当前行动者，**When** 该玩家尝试提交出牌，**Then** 服务端拒绝且对局状态不变。

---

### User Story 4 - 实时叫牌与打牌（合并明手、托管、超时）（Priority: P1）

四名占用者按桥牌规则完成叫牌与打牌：合法叫品、加倍/再加倍、明手摊牌、跟牌义务、赢墩判定、
庄家代打明手；机器人按配置节奏行动。

**Why this priority**: 这是「联网游戏」的主体体验；没有它前三个故事只有空壳。

**Independent Test**: 全机器人房间自动跑完一副，记录中 13 墩齐全、得分与 `core/scoring` 一致。

**Acceptance Scenarios**:

1. **Given** 发牌完成，**When** 叫牌结束于 3NT，**Then** 系统正确判定庄家、明手与首攻者。
2. **Given** 首攻落地，**When** 任意玩家查看快照，**Then** 明手牌对所有人可见，且只有庄家的占用者可以打明手牌。
3. **Given** 玩家在跟牌时点击非领出花色的牌，**When** 提交，**Then** 服务端拒绝并返回「必须跟出领出花色」。
4. **Given** 四家连续 Pass，**When** 第四家 Pass 落地，**Then** 本副记为流局，按贴点/MP 规则结算。

---

### User Story 5 - 成绩统计与复盘（Priority: P2）

比赛结束后（或每副结算后），玩家能查看逐副成绩、累计 IMP/点数/MP%、排名，并把任一副完整回放
（四手牌、叫牌表、逐墩出牌）。

**Why this priority**: 需求明确要求「记录叫牌打牌过程，最后统计成绩」；也是信任基础。

**Independent Test**: 跑完 12 副后打开成绩页，逐副 IMP 之和等于总计；打开第 3 副回放，四手牌各 13 张、
叫牌与出牌序列与记录一致。

**Acceptance Scenarios**:

1. **Given** 已完成 6 副，**When** 打开成绩页，**Then** 每副显示定约、结果、NS/EW 得分、IMP 与贴点后点数。
2. **Given** 比赛结束，**When** 打开历史记录，**Then** 服务端已落盘该场比赛 JSON，重启服务后仍可查询。
3. **Given** MP 模式，**When** 查看某副，**Then** 显示对照场 7 桌结果与本次得分百分比。

---

### User Story 6 - 大厅与进行中比赛列表（Priority: P3）

玩家在大厅看到「我的进行中比赛」与「最近完成比赛」，可一键回到未结束的房间。

**Why this priority**: 提升可用性，但不阻塞核心玩法。

**Independent Test**: 建房后刷新页面，大厅显示该房间并可点击返回。

**Acceptance Scenarios**:

1. **Given** 玩家有一个进行中的房间，**When** 刷新浏览器，**Then** 大厅列出该房间并提供「回到牌桌」。

---

### Edge Cases

- **同一玩家重复开两个标签页**：以最新连接为准，旧连接被标记为重复并断开（或只读），不得产生两个行动者。
- **房主离开未开赛的房间**：房主身份转移给最早加入的真人；无真人时房间销毁。
- **开赛后有人永久离开**：座位由托管机器人接管（继承该玩家的人格默认值），保证比赛可完成。
- **非法动作**（不是你的轮次、叫品低于当前叫品、跟牌违规、加倍无资格）：返回错误码 + 提示，状态不变。
- **结算竞态**（两个客户端同时提交）：服务端串行处理，第二次提交因轮次已前进而被拒绝。
- **副数为 12/18/24 以外的值**：拒绝创建房间。
- **同一副重复开局**：以 `matchId + boardIndex` 为幂等键，重复开副不会重发牌。

## Requirements *(mandatory)*

### Functional Requirements

**房间与座位**

- **FR-001**: 系统 MUST 允许玩家仅凭昵称创建设备级身份（`playerId` + `token`），无需密码。
- **FR-002**: 系统 MUST 允许创建房间，生成 6 位大写字母数字房间码，并指定副数（12/18/24）与计分模式（`mp` 双人赛 / `hcp-points` 贴点制）。
- **FR-003**: 系统 MUST 允许房主在开赛前把任意座位设为：自己、邀请真人（空位）、AI 机器人（含人格配置）。
- **FR-004**: 系统 MUST 允许第二名真人通过房间码加入并选择空座位；座位占用变化实时同步给房内所有人。
- **FR-005**: 系统 MUST 在 4 个座位全部占用后才允许房主开赛；开赛后座位与计分模式不可再改。
- **FR-006**: 系统 MUST 支持断线重连：同一 `playerId + token` 重连后恢复座位、手牌与当前视角快照。
- **FR-007**: 系统 MUST 在真人永久离开时用机器人接管其座位，保证比赛可继续完成。

**机器人人格**

- **FR-008**: 系统 MUST 支持机器人人格字段：名字、风险偏好（0 保守 / 1 正常 / 2 激进）、叫牌体系（`precision` / `natural`）、附加约定开关（至少：强无将、负加倍、弱二开叫）、随机度。
- **FR-009**: 系统 MUST 让机器人人格只影响动作选择，不改变合法性判定。
- **FR-010**: 系统 MUST 在机器人使用约定叫品时生成提醒文本，并随叫牌记录广播。
- **FR-011**: 系统 MUST 保证机器人行动节奏由服务端控制（可配置延迟），且在机器人行动期间对局状态不可被真人抢占。

**对局**

- **FR-012**: 系统 MUST 按标准复式轮转生成每副的庄家与局况（16 副循环表），并按比赛副数截取。
- **FR-013**: 系统 MUST 由服务端生成并保存每副的 `seed`，使得同一种子可完整复现发牌。
- **FR-014**: 系统 MUST 服务端校验叫牌合法性（层级、加倍/再加倍资格、轮次）。
- **FR-015**: 系统 MUST 服务端校验出牌合法性（轮次、跟牌义务），并在首攻后公开明手。
- **FR-016**: 系统 MUST 只允许庄家的占用者代打明手，明手本人不得直接出牌。
- **FR-017**: 系统 MUST 在每副结束后按标准复式计分计算 NS/EW 得分；流局双方 0 分。
- **FR-018**: 系统 MUST 支持两种比赛计分：
  - `hcp-points`：本副点数 = IMP −（胜方联手大牌点 − 20），逐副累加；
  - `mp`：以同一发牌的 7 桌机器人对照场结果计算比赛分百分比。
- **FR-019**: 系统 MUST 在每副结算后广播结算结果，并在全部副数完成后结束比赛。

**记录与统计**

- **FR-020**: 系统 MUST 为每副记录：副号、发牌种子、庄家、局况、四手牌、逐条叫牌、逐张出牌、定约、结果墩数、得分、IMP、点数/MP、对照场（MP 模式）。
- **FR-021**: 系统 MUST 在比赛结束后把完整记录以 JSON 落盘，并可经 HTTP 接口按 `matchId` 查询。
- **FR-022**: 系统 MUST 提供成绩页：逐副明细、累计点数、MP 百分比、胜负判定。
- **FR-023**: 系统 MUST 提供单副复盘：四手牌、叫牌表、逐墩出牌表。

**视角隔离**

- **FR-024**: 系统 MUST 按接收者视角裁剪快照：仅包含自己的手牌、公开信息、明手牌与本副结束后的四手牌。
- **FR-025**: 系统 MUST 不向任何客户端下发他人的机器人人格以外的隐藏信息（如发牌种子在开副前不得下发）。

**兼容性**

- **FR-026**: 系统 MUST 保留现有单人 MVP 功能，作为 `/solo` 路由可继续使用，且既有测试不被破坏。

### Key Entities

- **Player**：设备身份，`playerId`、昵称、token、最近连接时间。
- **Room**：房间，`code`、房主、座位表、比赛配置、状态（lobby / playing / finished）。
- **Seat**：座位占用，`kind`（human / bot / open）、`playerId` 或 `BotPersona`。
- **BotPersona**：名字、风险偏好、叫牌体系、约定开关、随机度。
- **Match**：一场比赛，`matchId`、配置、副数、当前副号、成绩汇总、状态。
- **Board**：一副牌，副号、seed、dealer、vulnerability、发牌、叫牌、出牌、定约、结果、计分明细。
- **Standing**：成绩行，NS/EW 归属、逐副得分、累计 IMP/点数/MP。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 单人（三个机器人）可在 2 分钟内完成建房到第 1 副开叫，全程无需文档。
- **SC-002**: 两名真人 + 两名机器人完成 12 副比赛，无需刷新页面；断线重连成功率 100%（测试覆盖 1 次断线）。
- **SC-003**: 每副结算后，逐副 IMP 之和与总计误差为 0；MP 百分比可复算一致。
- **SC-004**: 视角裁剪 0 泄漏：任何玩家快照中不出现未公开的他人手牌（自动化断言）。
- **SC-005**: 服务端对非法动作 100% 拒绝且状态不变（覆盖叫牌/出牌/轮次/明手四类）。
- **SC-006**: 同一 `seed` 重放同一副，机器人的叫牌与出牌序列完全一致。
- **SC-007**: 现有单人 MVP 的 200+ 单元测试保持通过，`/solo` 行为不变。

## Assumptions

- 一期为单服务进程、内存态 + 文件持久化；不引入数据库与分布式部署。
- 浏览器需支持 WebSocket 与 ES2022；移动端适配不在本期（沿用现有桌面布局）。
- 对照场机器人统一使用「正常风险 + 精确体系 + 随机度 0」，保证 MP 结果可复现。
- 比赛不设时限/超时判负；机器人接管仅用于真人离开场景。
- 网络时延按 < 200ms 设计；服务端广播以「全量快照」为主，实现简单优先。
- 二期（队式赛/全场赛）复用本期座位、比赛、记录模型，不要求本期实现。
