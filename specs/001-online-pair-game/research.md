# Research & Decisions: 联网双人赛（一期）

**Date**: 2026-11-01 | **Feature**: `001-online-pair-game`

本文件记录计划阶段的关键技术调研与取舍，供实现与复核使用。

## D1. 实时通信：`ws` vs Socket.IO vs SSE + HTTP

- **结论**：使用原生 `ws`，自定义 JSON 报文（`{ v, t, ... }`），服务端主动推送全量快照。
- **理由**：双向低延迟；依赖轻；协议完全可控，便于把「动作意图」与「视角快照」做严格区分。
- **放弃**：Socket.IO 自带房间/重连/降级，但会把连接语义藏在库内，且体积大；SSE 无法承载上行动作。
- **代价**：需要自己实现心跳、重连、重复连接处理 → 用 `playerId + token` 与 25s ping 解决。

## D2. 状态同步：全量快照 vs 增量事件

- **结论**：服务端在每次状态变更后，向房内每个连接发送**该视角的全量快照**（`room` 报文）。
- **理由**：一帧约 3–10KB（24 副记录不全量下发）；实现简单、天然抗丢包；重连只需一次快照。
- **放弃**：增量 patch/事件重放 → 需要版本向量与回放逻辑，一期收益低。
- **注意**：快照只含当前副 + 已完成副的摘要；逐副完整记录走 HTTP。

## D3. 视角投影（关键安全边界）

- **结论**：`server/view.ts` 是唯一生成对外快照的模块；`BoardView` 含
  `yourHand`、`dummyHand`、`revealedHands`，其余手牌字段不存在。
- **规则**：
  - 自己的手牌：始终可见；
  - 明手：首攻落地后对全桌可见；
  - 四手牌：仅本副 `phase === 'scored'` 后通过 `revealedHands` 下发（用于复盘）；
  - `seed`、对手手牌、机器人内部风格参数：不下发（人格配置为公开信息，可用于 UI 展示）。
- **测试**：`view.test.ts` 遍历每位玩家，序列化快照后断言不含他人手牌与 seed。

## D4. 双人赛（MP）如何在一桌上产生百分比

- **结论**：每副牌在服务端用**同一 seed 发牌**模拟 7 桌全机器人对局（正常/精确/随机度 0），得到 7 个 NS 分数；
  本桌结果与每个对照结果比较：胜 1、平 0.5、负 0，`MP% = 得分 / 7 × 100`。
- **理由**：单桌也能给出名次与百分比；完全可复现；计算量小（7 × 32 次 AI 决策，毫秒级）。
- **存储**：对照场结果写入 `BoardRecord.referenceResults`，成绩页展示，可离线复算。
- **边界**：流局按 0 分参与比较；对照场与主桌使用同一副轮转与局况。

## D5. 复式轮转（庄家/局况）

- **结论**：采用标准 16 副轮转表：第 n 副庄家 `ORDER[(n-1) % 4]`，局况按标准序列
  （1-4 无、5-8 NS、9-12 EW、13-16 双有，实际按标准表实现）。
- **理由**：与 `docs/` 及常规复式赛一致；12/18/24 副从该表截取/循环。
- **实现**：`shared/matchSchedule.ts` 导出 `scheduleFor(boardIndex)`，纯函数、可测。

## D6. YAML 规则在 Node 侧加载

- **问题**：现有 `src/engine/loader.ts` 使用 Vite `import.meta.glob(?raw)`，Node 无法执行。
- **结论**：抽出 `src/engine/parse.ts`（`parseBiddingRules` / `parseLeadRules` / 校验函数），
  `loader.ts` 保留浏览器加载与 localStorage 覆盖；`server/rules.ts` 用 `fs.readFileSync` + `parse.ts`。
- **理由**：解析逻辑单点复用；两端行为一致（宪法 III）。
- **兼容**：`loader.ts` 继续 re-export parse 函数，既有 import 不必改动。

## D7. 身份与重连

- **结论**：客户端首次访问生成 `playerId`（`crypto.randomUUID()`）与 `token`（随机 32 hex），存 `localStorage`；
  服务端在内存中绑定 `playerId → token`，重连时校验并恢复座位。
- **理由**：免注册、够用；token 只用于本机重连，不作为强安全边界（一期无金钱/排名利益）。
- **风险**：清缓存即失去座位 → 由「真人离开 → 机器人接管」兜底。

## D8. 机器人人格映射

| 人格字段 | 映射 |
|----------|------|
| 风险偏好 `conservative/normal/aggressive` | `SeatStyle.bid/play = 0/1/2` |
| 叫牌体系 `precision/natural` | 规则文件 `precision.yml` / `natural.yml` |
| 随机度 `0..1` | `SeatStyle.randomness` |
| 约定开关 | 叫牌时对约定叫品附加 `alertText`（提醒文本），并在规则匹配时作为标签过滤（见 personas.ts） |

- **约定实现**：一期约定开关用于 (a) 生成提醒文本；(b) 通过 `conventions` 影响 `bidAI` 的候选动作集合
  （例如关闭「负加倍」时，把带 `negative_double` 标签的候选剔除）。
- **理由**：避免重写规则引擎；标签过滤是 `BiddingRule` 上已有的扩展位。

## D9. 机器人接管（真人离开）

- **结论**：真人座位的占用者离开房间超过 `TAKEOVER_MS`（默认 60s，测试可注入 0）后，服务端把该座位转为
  机器人（人格取该玩家创建时的默认：名字=玩家昵称，风险正常，体系精确，随机度 0）。
- **理由**：保证比赛能完成；与「AI 与真人同权」一致。
- **一期简化**：只在 `lobby` 阶段允许房主移除/替换座位；开赛后主动离开立即由机器人接管，仅断线（未主动离开）保留座位等待重连。

## D10. 持久化格式

- **结论**：比赛完整结束后写入 `server/data/matches/<matchId>.json`，含 `schemaVersion`、配置、座位、
  逐副完整记录与成绩。提供 `GET /api/matches/:id` 与 `GET /api/matches?limit=`。
- **理由**：可被外部工具读取，满足「记录叫牌打牌过程」与重启后查询。
- **注意**：写入采用「临时文件 + rename」避免半截文件。
