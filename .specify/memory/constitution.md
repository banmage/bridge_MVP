# 桥牌联网对局项目 Constitution

> 本宪法适用于 `bridge_MVP` 从「单人 MVP」演进为「联网对局平台」的全部工作。
> 单人 MVP 的既有契约（见 `README.md` 与 `docs/`）在未被本宪法或新规格显式替代前继续有效。

## Core Principles

### I. 服务端权威（Server-Authoritative）

一切影响对局结果的状态变更（发牌、叫牌合法性、出牌合法性、赢墩、结算、轮转）**必须**由服务端裁决。
客户端只提交「意图」（我要叫 1NT / 我要出 ♠A），不得提交「结果」（我赢了 3 墩、我得分 420）。

- 客户端可以为了体验做本地预校验，但服务端必须重新校验，且以服务端结果为准。
- 任何客户端发来的非法动作一律拒绝并返回可读错误，不得使对局状态发生部分变更。
- 计时、AI 思考延迟等节奏控制属于服务端职责，客户端不得通过伪造时间来抢先行动。

### II. 视角隔离与信息公平（Information Hiding）

服务端下发的每一份快照**必须**按接收者视角裁剪，禁止「先全量下发、客户端隐藏」的做法。

- 玩家只能看到：自己的手牌、公开叫牌、已发生的出牌、明手牌（首攻后）、本副结束后才可见的四手牌。
- 机器人人格配置、发牌种子、未到公开时机的隐藏信息不得出现在其他玩家的报文里。
- 自动测试必须包含「视角裁剪」用例：未公开信息不得出现在他人快照中。

### III. 规则单点复用（Single Source of Rules）

叫牌/打牌法律、计分、IMP/贴点、AI 决策**只有一份实现**，前端与后端共用 `src/core`、`src/engine`、`src/ai`。

- 禁止在服务端复制一份叫牌/跟牌合法性代码；服务端直接引用同一套模块。
- 与运行环境相关的部分（YAML 读取、网络、存储）必须显式隔离：
  - `src/engine/parse.ts`（纯文本解析）与 `src/engine/loader.ts`（浏览器 `?raw`）分离；
  - 服务端通过 `server/rules.ts` 读文件，不得 import 浏览器专有模块。
- 计分口径一旦确定即冻结，任何变更必须同时更新宪法、规格与测试。

### IV. 全量可复盘（Auditable Records）

每一副牌**必须**完整记录并可复查：牌型、发牌种子、逐条叫牌、逐张出牌、局况、定约、得分与计分模式。

- 记录在比赛结束（或每副结算后）落盘，格式稳定、可被外部工具读取（JSON）。
- 记录中必须包含计分依据（IMP、贴点调整、MP 百分比与对照场）。
- 任何「本副结果」都能仅凭记录复现；复盘不得依赖当前内存状态。

### V. AI 与真人同权（Bots Are First-Class Seats）

机器人是座位的一种占用者，与真人共享同一套动作入口与合法性约束。

- 机器人人格**必须**可配置：名字、风险偏好（保守/正常/激进）、叫牌体系、附加约定。
- 机器人不得拥有规则外能力（不能看他人手牌、不能跳过跟牌义务、不能绕过叫牌层级）。
- 机器人配置只影响「选择哪个合法动作」，不得影响「动作是否合法」。

### VI. 可确定性测试（Deterministic by Seed）

随机性必须可播种、可复现；核心路径必须有单元/集成测试。

- 发牌、AI 随机度、对照场模拟一律使用可播种随机源。
- 服务端对局引擎必须能在无网络、无计时的纯函数方式下被测试。
- 新增法律/计分/AI 行为必须附带测试；`npm test` 与 `npm run typecheck` 必须常绿。

### VII. 增量交付（Incremental Delivery）

一期只交付「双人赛 / 贴点制、单桌 4 座、真人+机器人混排、成绩与复盘」；二期才做队式赛/全场赛。

- 每个用户故事必须可独立演示、独立验收。
- 为二期预留接口（座位抽象、比赛模式枚举、成绩模型），但不得为假设中的二期需求过度设计。
- 任何超出规格的功能需先更新规格再实现。

## 技术与架构约束

- **前端**：TypeScript + Vue 3 + Vite + Pinia（沿用现有 MVP）。
- **服务端**：Node.js + TypeScript，单进程内存态 + 文件持久化；WebSocket 承载实时协议。
- **共享层**：`src/core`、`src/engine`、`src/ai`、`src/models`、`shared/` 为前后端共享代码；禁止在其中引入 DOM/Node 专有 API。
- **传输**：协议报文必须带版本号与类型判别字段；所有报文类型定义集中在 `shared/protocol.ts`。
- **持久化**：比赛记录以 JSON 落盘（默认 `server/data/matches/`），不引入数据库（一期）。
- **依赖**：新增运行时依赖需在计划阶段说明理由；能用标准库/现有依赖解决的不引入新包。

## 质量门禁

1. `npm test`：全部单元/集成测试通过（前端 + 服务端对局引擎）。
2. `npm run typecheck` 与 `npm run typecheck:server`：零类型错误（`strict`）。
3. 新增法律/计分/视角裁剪逻辑必须有对应测试用例。
4. 每副牌结束后，记录必须能通过复盘接口完整还原。
5. 服务端对任意非法动作必须返回错误且对局状态不变（有测试）。

## 开发流程

1. 需求变更先写入 `specs/<feature>/spec.md`，再进入计划与实现。
2. 计划需包含：数据模型、协议契约、验收映射、迁移/兼容策略。
3. 任务按用户故事优先级（P1 → P3）拆分，每个任务可独立验证。
4. 实现顺序：共享法律层 → 服务端引擎 → 协议/会话 → 客户端界面 → 记录与统计。
5. 兼容策略：单人 MVP 保留为 `/solo` 路由，联网功能不得破坏其测试与行为。

## Governance

- 本宪法优先于个人编码习惯；与既有文档冲突时，以本宪法 + 最新规格为准，并回写文档。
- 修改宪法需说明理由、影响范围与迁移方案，并同步更新版本号与日期。
- 所有验收必须可复现：给出发牌种子与操作序列。
